## Section B — Problems, by severity

### 🔴 Blocks teamwork / reproducibility

**B1. The new pipeline is not on `main`.**
- *What:* `main` (last commit `78cae57`, Wahbi) is the old project. `git diff --stat main feature/pipeline-mlops` shows 27 changed files (+5 342 / −4 220): DVC pipeline, `src/` modules, tests, Docker and CI changes are only on `feature/pipeline-mlops`. A separate remote branch `origin/feature/olive-data-pipeline` (commit `772927f`, kenzaa2002, "Add olive data pipeline and preprocessing") exists and is not merged.
- *Why it matters:* a teammate who clones `main` gets code that does not match the README, and CI only tests `main` and PRs.
- *Fix:* do not merge by hand. Finish the items below, push, then open a Pull Request `feature/pipeline-mlops → main` and merge when CI is green. Ask about `olive-data-pipeline` (C).

**B2. `mlflow.db` (a binary SQLite file) is committed to Git.**
- *Where:* `mlflow.db` (tracked since the first commit `322e9d7`). `.gitignore` does not list it.
- *Evidence (read-only query):* experiments are `0 Default` and `1 olive-disease` with `artifact_location = /kaggle/working/mlartifacts_olive`. 4 runs. The experiment `olive-disease-pipeline` used by `train.py` does **not** exist yet. `mlartifacts/` is not on disk, so the artifacts of these 4 runs are lost — only metrics and params can be migrated.
- *Why it matters:* two people changing a binary DB = a conflict Git cannot merge. It also contains Kaggle paths from someone else's machine.
- *Fix:*
  ```bash
  cp mlflow.db ../backup-mlflow.db        # keep a copy outside the repo
  git rm --cached mlflow.db               # stop tracking it, keep the file on disk
  echo "mlflow.db" >> .gitignore
  ```

**B5. The MLflow address is hard-coded and overrides the environment variables.**
- *Where:* `configs/config.yaml:48` (`mlflow_uri: sqlite:///mlflow.db`), `src/models/train.py:118` and `src/models/test.py:90` (`mlflow.set_tracking_uri(...)`), `src/models/train.py:120-121` (`create_experiment(..., artifact_location=(RACINE / "mlartifacts").as_uri())`).
- *Why it matters:* MLflow gives priority to `set_tracking_uri()` over the `MLFLOW_TRACKING_URI` environment variable. So putting the DagsHub URL in `.env` would be **silently ignored** and everybody would keep writing to a local file. `sqlite:///mlflow.db` is relative to the folder you run from, so running from another folder creates a new empty DB. The `artifact_location` writes an absolute path (`file:///C:/Users/...`) into the experiment, which breaks on other machines and on DagsHub.
- *Fix:*
  ```diff
  # src/models/train.py
  -    mlflow.set_tracking_uri(suivi["mlflow_uri"])
  -    nom_exp = suivi["experience_pipeline"]
  -    if mlflow.get_experiment_by_name(nom_exp) is None:
  -        mlflow.create_experiment(nom_exp, artifact_location=(RACINE / suivi["dossier_artefacts"]).as_uri())
  -    mlflow.set_experiment(nom_exp)
  +    mlflow.set_experiment(suivi["experience_pipeline"])   # créée automatiquement si absente

  # src/models/test.py
  -    mlflow.set_tracking_uri(config["suivi"]["mlflow_uri"])
  ```
  ```diff
  # configs/config.yaml
   suivi:
  -  mlflow_uri: sqlite:///mlflow.db
     experience: olive-disease
     experience_pipeline: olive-disease-pipeline
  -  dossier_artefacts: mlartifacts
  ```
  Also: Python does **not** read a `.env` file by itself. Add `python-dotenv` to `requirements.txt`, and at the top of `src/utils.py`: `from dotenv import load_dotenv; load_dotenv(RACINE / ".env")`. Or each teammate runs `set -a; source .env; set +a` before `python`.

**B6. `.env` is not git-ignored (and does not exist yet — good time to fix it).**
- *Where:* `.gitignore` only ignores `frontend/.env.local` (line 22). No rule for `.env`.
- *Why it matters:* the DagsHub token would be committed by a simple `git add .`. Once a token is in Git history it must be revoked, even after deletion.
- *Fix:* add the rules in Section E **before** creating `.env`.

**B7. `dvc.yaml` misses dependencies → models can be silently stale.**
- *Where:* `evaluation` (`dvc.yaml:47-56`) depends only on `src/models/test.py`. But `test.py` imports `src/models/train.py` (`test.py:33`: `OliveDataset, charger_donnees, predire`), `src/features/feature_extraction.py` (`test.py:31`), `src/models/architectures.py`, and `src/utils.py`. Changing those files does **not** re-run evaluation. `entrainement` (`dvc.yaml:22-45`) and `preparation` (`dvc.yaml:10-21`) miss `src/utils.py` (seed, config loader, git commit). `preparation` depends on `data/raw`, which is not DVC-tracked, so DVC cannot detect changes to the images.
- *Why it matters:* the target "models only via `dvc repro`" is only true if DVC knows every input. Otherwise someone changes the preprocessing, runs `dvc repro`, and gets **nothing** re-run.
- *Fix:* see the corrected `dvc.yaml` in Section E.

### 🟠 Should fix

**B8. PNG files are declared under `plots:`.** `dvc.yaml:72-76`. DVC's `plots` are meant for data files it can draw (CSV, JSON, YAML). A PNG is just a file: it belongs under `outs:`. Fixed in Section E.

**B9. Results are not reproducible across machines, even with seeds.**
- *Where:* seeds are set only in training (`train.py:87`, via `fixer_graine` in `src/utils.py:27-33`). `test.py` never seeds: `temps_cpu_ms` (`test.py:52`) and the ONNX check (`test.py:64`, `:68`) use random tensors. `fixer_graine` does not set `torch.backends.cudnn.deterministic = True`.
- *Why it matters:* even with the same seed, a CPU and a GPU give different weights. DVC will see two different `models/*.pt` files. This is normal, but the team must know: **only one person trains; the others `dvc pull` the model.**
- *Fix:* in `src/utils.py`, inside `fixer_graine`, add `torch.backends.cudnn.deterministic = True` and `torch.backends.cudnn.benchmark = False`. In `test.py`, call `fixer_graine(params["decoupage"]["seed"])` at the start of `main()`.

**B10. Dependencies are not pinned.**
- *Where:* `requirements.txt:5-30` uses `>=` everywhere (e.g. `torch>=2.3`, `mlflow>=2.14`, `dvc>=3.50`). `api/Dockerfile:11` installs torch/torchvision without any version. `requirements-api.txt` has no torch at all. CI, Docker and each laptop can get different versions.
- *Why it matters:* different PyTorch or MLflow versions can give different metrics and different ONNX outputs; `dvc repro` on two machines is not comparable.
- *Fix:* in a fresh venv, install and run `pip freeze > requirements-lock.txt`; keep `requirements.txt` for humans and use the lock file for reproducible installs. Put the same torch version in `api/Dockerfile`.

**B11. Unknown class labels silently become class 1.**
- *Where:* `src/models/train.py:55`: `y = splits["classe"].map(lambda c: index.get(c, 1))`.
- *Why it matters:* a typo in `splits.csv` (e.g. `Healthy` vs `healthy`) or an unexpected folder would become class 1 (`aculus`) with no error. Training would run "successfully" on wrong labels.
- *Fix:*
  ```diff
  -    y = splits["classe"].map(lambda c: index.get(c, 1)).to_numpy()   # "malade" -> 1 (binaire)
  +    def indice(c):
  +        if c == "malade":                     # Zeytin uniquement, évaluation binaire
  +            return 1
  +        if c not in index:
  +            raise ValueError(f"Classe inconnue dans splits.csv : {c!r}")
  +        return index[c]
  +    y = splits["classe"].map(indice).to_numpy()
  ```

**B12. The deployed model is chosen in two places; some config keys are unused.**

The deployed model is chosen by `deploye: true` in `configs/param.yaml:33`, read by `src/models/test.py:101`. `configs/config.yaml:15` (`donnees.images_preparees`) is never read: `src/features/feature_extraction.py:57-58` hard-codes `data/processed/images_224.npy`. `projet.nom` (`config.yaml:4`) is not read anywhere.
- *Why it matters:* changing a value in the config does nothing, which is confusing for teammates.
- *Fix:* delete `modele_deploye.architecture` and `projet.nom`. Make `chemin_images_preparees()` read `config["donnees"]["images_preparees"]`, or delete that key.

**B13. The API loads a file path, not the MLflow registry, and the registry is not used anywhere.**

- *Why it matters:* the target setup (`models:/<name>@champion`) needs code that registers the model and a container that can reach DagsHub with credentials.
- *Fix:* later step (Section D, step 14). Not urgent until the pipeline runs.

**B14. Old run IDs stored in models will break on the shared server.**
